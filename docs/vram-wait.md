# VRAM アクセスウェイト

MZ-2500 は VRAM を CPU と G-CRTC で共有しており、CPU 側のアクセスには
バンクごとの固定ウェイトと、表示期間のストールがかかります。ストールが
かかるかどうかは、そのラスタでコントローラがそのレイヤをフェッチして
いるかで決まります。本エミュレータはこの 3 点をすべて実装しています
(`core/vram_wait.h`、`core/gcrtc.h`、`Mz2500::charge_access_wait()`)。

## 1. バンクごとの固定ウェイト

`MZ2500_IO_Map.pdf` のポート B5h メモリブロック表「アクセス時のウェイト」
欄がそのまま実装値です。

| バンク | 内容 | ウェイト |
| --- | --- | --- |
| 00h-1Fh | メイン RAM / 拡張 RAM | M1 サイクル時 +1 (Z80 コアが元から計上) |
| 20h-27h | 標準グラフィック VRAM | +1 |
| 28h-2Fh | 拡張グラフィック VRAM | +1 |
| 30h-31h | 標準グラフィック VRAM (リードモディファイライト) | +2 |
| 32h-33h | 拡張グラフィック VRAM (リードモディファイライト) | +2 |
| 34h-37h | IPL ROM | M1 サイクル時 +1 |
| 38h | テキスト VRAM | +1 |
| 39h | 漢字 ROM / PCG | +2 |
| 3Ch-3Fh | 通信 ROM | M1 サイクル時 +1 |

「M1 サイクル時 +1」はオペコードフェッチそのもののコストなので、
本エミュレータでは追加しません。追加すると RAM 全体が二重に遅くなります。

## 2. 表示期間のストール

同じ表の脚注が本命です。

> (\*) M1 サイクルは不可能。表示期間中にアクセスすると、帰線期間まで
> 別途ウェイトがかかる。

G-CRTC は画面を描くあいだ VRAM を読み続けていて、帰線期間だけ CPU に
バスを譲ります。したがって表示期間中に出した VRAM アクセスは失敗せず、
**次の帰線期間の先頭まで待たされてから完了します**。

- 表示ラスタ (0〜399 ライン) では、行末の水平帰線期間まで待たされます。
- 垂直帰線期間 (400 ライン以降) では G-CRTC が走査していないので、
  1 行まるごと CPU のものです。ストールはありません。

### ラスタ幾何

24kHz モードのフレームは 448 ライン、うち 400 ラインが表示です
(`core/timing.h`)。55.486447Hz で 448 ラインなら水平周波数は 24.86kHz、
1 ラインは 6,000,000 / 24,858 = **241.4 サイクル**になります。

448 は 55.5Hz 近辺のどのフレーム長も割り切りません。それが正しい姿で、
ドットクロックは CPU クロックの整数倍ではないため、実機のライン境界は
CPU サイクルの途中に落ちます。そこで本コアは**フレーム長 108,160 サイクル
を定数とし、ライン境界をそこから割り出します** (`line_start_cycle()`)。
1 ラインは 241 サイクルと 242 サイクルが交互に現れ、平均 241.43 です。
フレームレートは 55.473Hz で、実機の 55.486447Hz に対して 0.024% 遅い
だけです。

### 帰線期間の長さ

同時代のディスクマガジンに載った VRAM アクセスの実測記事は、
6MHz 換算で**水平走査期間が約 170 ステート、水平帰線期間が約 70 ステート**
(1 ライン約 240 ステート) と書いています。本コアの `HBLANK_CYCLES` は
この実測値そのままの 70 です。

公称ドットタイミング (1 ライン 864 ドット中 200 ドットが帰線 = 23.1%) から
換算すると 56 サイクルになりますが、採りません。記事の 70/240 = 29.2% は
**CPU から見た窓の直接測定**であり、ウェイトモデルが必要としているのは
まさにそれだからです。

I/O マップが引く X1 センターの数値
「24kHz: メモリライトサイクル + 50 クロック + メモリライトサイクル /
15kHz: メモリライトサイクル + 91 クロック + メモリライトサイクル」も
矛盾しません。Z80 のメモリライトサイクルは 3 ステートなので、24kHz では
3 + 50 + 3 = 56 ステートぶんの仕事が窓に確実に収まる、という保証値で、
70 ステートの窓に 14 ステートの余裕を残した言い方になります。
また X1 センターは「リードモディファイライトの +1/+2 を足しても
上の値は変わらない」とも書いており、固定ウェイトは窓の内側で払われる
=== 窓を縮めない、と解釈しています。

## 3. 表示していないラスタではウェイトがかからない

実測記事は高速化テクニックとして次のように書いています。

> ハードウェアビューポートで表示領域を制限する。ディスプレイに表示さえ
> しなければ、ウェイトはかかりません。全画面を消す必要はなくて、一部分
> だけでも、制限した分だけウェイトが外れます。ただ x 方向に制限しても
> 意味はないので、y 方向に制限してください
> (結局ラスター単位に制御するということです)。

**表示していないラスタは、コントローラが VRAM をフェッチしていない
ラスタ**です。したがってそのラスタではバスを握られておらず、ストールも
かかりません。x 方向の制限が効かないのは、水平方向を削ってもコントローラ
は 1 ライン分バスを占有し続けるからです (`GDEHS/GDEHE` は見ません)。

**レイヤごとに別々のゲート**です。

| バンク | レイヤ | 表示窓 |
| --- | --- | --- |
| 20h-33h | グラフィック | G-CRTC の `GDEVS/GDEVE` (08h-0Bh) + モードレジスタ 0Eh |
| 38h/39h | テキスト / PCG / 漢字ROM | CRTC の垂直テキスト窓 (03h SL / 05h EL) |

分かれていることは記事のサンプルプログラム自身が証拠です。

> ただ、グラフィックを完全にマスクしてしまったらウェイトがかからなく
> なりますので、このプログラムではテキスト画面でウェイトをかけています。
> ですから console@ などで、テキストをマスクすると正常動作しなくなるので
> 注意してください。

グラフィックを全マスクしてもテキスト側でウェイトが取れる、しかし
console@ (＝ CRTC 03h/05h) でテキストも消すと取れなくなる。この 2 つが
同時に成り立つのは、両レイヤが別の窓で個別にゲートされている場合だけです。

`GDEVS/GDEVE` は表示ラインを数えるので、200 ライン系モードでは 1 ライン
= 2 ラスタになります (フレームコンポーザと同じ対応)。CRTC 03h/05h は
2 ラスタ単位・先頭が 17 (11h) で、これもコンポーザと同じ解釈です。
共通語彙は `core/gcrtc.h` に置いてあります。

## 効いてくるところ

- VRAM を連続で叩くルーチンの速度は、帰線期間の長さで頭打ちになります。
  ディスクから VRAM への直接転送が実機でオーバーランするのはこのため
  です。
- 逆に「VRAM を触るとかならず帰線期間に出る」ので、水平帰線期間の検出
  手段として使えます。ラスタ単位で G-CRTC の水平表示窓 (0Ch/0Dh) を
  書き換えて画面を任意の形にマスクする手法はこれを利用しています。
  この手法は 1 ラスタあたり 1 エントリで動くので、ラスタ幾何が
  1 サイクルでもずれると形が崩れます。上記の 448 ライン / 400 表示は
  実測記事に付属するサンプル (楕円マスク) で確認しました。

## テスト

- `tests/unit/test_vram_wait.cpp` — 64 バンク全部の固定ウェイトと、
  ストール量・垂直帰線での非課金・フレーム跨ぎを直接検証します。
- `tests/gmode/check_vramwait.sh` — 実機側の検証。テキスト VRAM を
  触った直後にポート F4h を読み、200 回すべてが水平帰線期間に出ること
  を確認します。ストールを外すと 200 回中 152 回が表示期間になります。
- `tests/gmode/check_vwinwait.sh` — 同じ測定ループを 6 通りの窓設定で
  回し、レイヤごとのゲートを検証します。窓が開いていれば 200/200 が
  帰線、閉じていれば表示期間が多数派、上 100 ライン分だけ開けた場合は
  その中間 (136/64)、モードレジスタでレイヤごと切っても外れる、
  そしてグラフィックを全マスクしてもテキストは待たされる。
